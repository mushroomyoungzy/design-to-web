# 디자인 읽는 법 (입력별)

## 피그마 링크

### 링크 풀기

- `figma.com/design/<fileKey>/<이름>?node-id=67-1840` → fileKey, nodeId `67:1840` (`-`를 `:`로)
- `/branch/<branchKey>/` 가 있으면 branchKey를 fileKey로

### 읽는 순서

1. `get_metadata` (nodeId 없이) → 페이지 목록
2. 링크한 노드가 있는 **페이지 전체** metadata → 같은 페이지의 다른 프레임(hover 상태, 펼침 상태, 전체메뉴, 서브페이지)까지 파악. 결과가 크면 파일로 저장된 것을 python으로 최상위 2~3단계만 뽑는다
3. `get_variable_defs` → 색·크기 변수
4. `get_comments` → 말풍선 댓글 (해결/미해결 구분)
5. `get_screenshot` → 전체 모습
6. 섹션 하나씩 `get_design_context` → 폰트, 크기, 간격, 텍스트, `data-interaction-annotations`(Interaction 주석)

### 놓치기 쉬운 것

- 페이지 전체 `get_metadata`는 하위 레이어가 빠진 채(자식 없는 프레임처럼) 나올 수 있다. 섹션의 텍스트·이미지 구성은 섹션별 `get_design_context`로 확인한 뒤 판단한다
- 레이어 이름이 대부분 `Frame`이면 내용을 보고 섹션 이름을 붙인다
- 피그마 변수가 없으면 design context의 hex 값을 모아 색 토큰을 만든다
- `BOOLEAN_OPERATION` 노드는 `use_figma`(읽기 전용)로 자식 도형의 위치·크기·모서리(`topLeftRadius` 등)와 fill 종류를 읽는다. fill이 `VIDEO`면 영상 자리다 (레이어명에 "영상"이 있어도 확인)
- 댓글은 `get_comments`로 읽을 수 있다. 댓글이 어느 페이지(pageId)에 달렸는지 확인하고, 링크한 페이지와 다르면 범위에 넣을지 묻는다
- 파일이 안 열리면 `whoami`로 연결된 계정을 확인한다 (그 계정에 공유가 안 된 파일)
- `use_figma`로 노드를 만들거나 지우는 작업은 하지 않는다. 남의 디자인 파일이고, 보기 권한만 있는 경우가 많다

### 값 확정

- 간격·크기·색은 metadata 좌표와 design context에서 **잰 값만** 쓴다. 임의로 넣지 않는다
- 섹션 간격은 프레임 y좌표 차이로 계산한다
- design context가 주는 React + Tailwind 코드는 **참고용**. 그대로 쓰지 않고 이 스킬의 규칙으로 새로 쓴다. 절대좌표로 그려진 요소는 웹 구조(flex/grid)로 다시 짠다
- 이미지·SVG 주소는 7일 뒤 만료되는 임시 주소. 실행 시 사용 금지, 파일로 받아 쓴다

### 프레임 해석

- 이름에 `_hover`가 붙은 프레임·레이어 = hover됐을 때의 모습. 기본 프레임과 비교해 달라진 점을 hover 스타일로
- `-cont`, `track`, `fullmenu` 등 = 펼침·전체 목록·오버레이 상태. 어느 섹션의 상태인지 연결한다
- 같은 콘텐츠가 작은 리스트와 큰 블록으로 두 번 그려져 있으면 **한 요소의 전후 상태**일 수 있다. 두 요소로 만들지 말고 묻는다
- 숨김(hidden) 레이어, `_old` 레이어는 제외
- 레이어명에 `Adobe Stock preview` 등 → 워터마크 미리보기 이미지라고 리포트에 표시

### 주석·레퍼런스

- **퍼블리싱 전에 반드시 모두 찾아 읽고 확인한다.** 빠뜨리면 시안과 다른 움직임을 만들게 된다
    - 말풍선 댓글: 링크한 페이지(`pageId`)의 `get_comments`. 위치(`node_offset` y)로 어느 섹션인지 맞추고, 첨부 이미지도 열어 본다
    - Interaction 주석: 섹션별 design context의 `data-interaction-annotations`, `use_figma`로 노드의 `annotations`
    - 레이어 이름 속 설명: `wordmark (이미지 영역 배경 롤링)`, `hero_image (롤링 3장)`, `빠른상담 (화면 하단 고정)`, `btn_prev (disabled)`처럼 괄호나 한글로 적힌 동작·상태. 숨김 레이어도 이름에 동작이 적혀 있으면 구현 대상이다
    - 캔버스 위 메모 텍스트(`참고`, `모션`, `http` 등이 들어간 TEXT 노드)
- 주석·댓글·메모에 **링크가 있으면 내장 브라우저로 직접 열어** 해당 부분의 움직임을 확인한다 (스크롤해서 여러 시점을 캡처). 열지 못하면 사용자에게 알리고 묻는다
- 확인한 주석·링크와 그걸 어떻게 구현했는지를 `<id>_spec.md`(리포트)의 섹션 표에 적는다. 결과를 알릴 때도 "주석 ○○를 이렇게 반영했다"고 짚는다
- Interaction 주석은 요소 구현에 반드시 반영하고, 최종 코드에는 주석 속성을 남기지 않는다
- 주석의 레퍼런스 사이트는 **움직임(로직)만** 참고한다. 마크업 구조·간격·요소 구성은 디자인이 기준. 레퍼런스 DOM을 따라가며 디자인 요소를 바꾸지 않는다
- 애니메이션이 필요해도 디자인의 `li`는 `li`로 남긴다. 자리를 지켜야 하면 `li`가 자리를 잡고(`aspect-ratio`) 자식만 `position: absolute`로 움직인다
- 움직임 디테일(속도, 이징)은 사용자 가이드가 우선, 없으면 레퍼런스를 보고 맞춘다

## JPG·PNG 시안

- 대화에 첨부한 이미지는 자동으로 줄어든다(가로 653 등). 폭이 1920보다 작으면 PC 폴더(바탕화면·다운로드)에서 같은 시안의 원본 파일을 찾아 크기를 확인하고(줄인 첨부본과 픽셀 비교) 원본으로 분석한다. 못 찾으면 원본 파일 위치를 묻는다
- 색은 글자 위가 아니라 면에서 뽑고, 글자색은 영역 안 가장 진한 픽셀로 뽑는다
- 원본 이미지가 없는 사진 자리는 연한 배경색 상자로 두어 레이아웃이 보이게 한다 (이미지가 들어오면 덮임)
- 이미지를 직접 보고 섹션을 나눈다. 너무 길면 섹션 단위로 잘라 확대해서 본다 (python PIL로 crop)
- 시안 폭을 먼저 확인한다 (보통 1920). 이미지 폭과 다르면 비율로 환산
- 수치는 픽셀을 재서 **추정**한다 → 4의 배수로 반올림. 리포트에 "추정값"이라고 표시하고, 확실하지 않은 값(폰트 크기, 굵기, 색)은 목록으로 묻는다
- 색은 픽셀 색을 뽑아 쓰되(PIL), 비슷한 색은 하나의 토큰으로 묶는다
- 폰트는 추정만 가능. 사용자에게 확인
- 사진·아이콘은 기본으로 시안에서 오려 쓰지 않는다. 사용자가 "임의로 넣어"라고 하면 **시안 원본(고해상도)에서 잘라 임시 이미지**로 넣는다: 사진 자리 경계는 흰 배경과의 차이로 자동 측정, 글자·버튼이 얹힌 사진은 OpenCV inpaint로 글자를 지움, 장식 그래픽은 흰 배경을 투명으로 뺌. 시안에 없는 자리는 비슷한 사진을 돌려 쓰고, 파일명은 원본과 같게 해서 나중에 덮어쓰면 교체되게 한다. 설명서에 임시라고 적는다
- 원본이 올 때까지는 빈 `<img>` 자리 + 필요한 이미지 목록을 리포트에 적어 원본을 요청한다
- hover·인터랙션은 알 수 없으므로 물어본다

## 다른 사람이 만든 HTML 가공

### 먼저 묻기

- 화면은 그대로 두고 코드만 정리할지, 반응형으로 새로 짤지 묻는다 (AskUserQuestion). 원본이 1920 고정 화면을 `zoom`·`transform: scale`로 통째로 줄이는 구조면 "반응형으로 새로 짜기"를 추천한다: PC는 원본과 같게, 그 아래는 `rules-interaction.md`의 분기점 기준
- 원본 파일은 사용자 첨부 원본을 복사해서 작업한다. 원본을 고치지 않는다

### 읽기

- HTML·CSS·JS를 **모두** 읽는다. 파일이 크면 이미지·폰트 data URI를 `DATA`로 바꾼 사본(body / style / script로 분리)을 만들어 읽는다
- 화면을 먼저 렌더해서(Playwright 1920 전체 스크린샷, 모바일 한 장) 원래 모습을 기준으로 삼는다. 비교할 때 기준 스크린샷과 같은 조건으로 찍는다 (`reducedMotion: 'reduce'`로 찍으면 등장 효과·자동 회전이 멈춰 비교가 쉽다)
- 원본의 배치 방식을 먼저 파악한다. 12열 grid에 모든 요소를 같은 행에 두고 `margin-top`으로 세로 위치를 박은 구조가 흔하다. 이 경우 각 요소의 시작·끝 좌표를 계산해 **요소 사이 간격**으로 바꾼다 (예: 제목 끝 352, 진행선 시작 432 → `margin-top: px-rem(80)`)
- 문구 오타, 같은 문구 반복, 같은 섹션 제목 중복을 찾아 "원본 그대로 둔 것"으로 적는다. 임의로 고치지 않는다

### 꺼내기

- data URI 이미지·폰트·인라인 SVG 로고는 파일로 꺼낸다: `assets/images/<id>/`, `assets/fonts/<id>/`. 폰트는 `<id>.scss` 맨 위 `@font-face`로 연결한다(미리보기에서도 그대로 동작)
- 반복되는 큰 블록(탭 패널 4개, 사례 5개, 카드 10개)과 SVG 아이콘은 원본에서 정규식으로 뽑아 새 마크업 틀에 끼워 넣는 생성 스크립트로 만든다. 내용을 손으로 다시 옮겨 적지 않는다 (오탈자·누락 방지)
- JSON 데이터(`<script type="application/json">`)는 내용 그대로 두고 id만 규칙에 맞춘다

### 다시 쓰기

- **보이는 결과는 유지하고 코드만 규칙에 맞게** 다시 쓴다
  - 클래스 → BEM, id → snake_case, `data-*` 훅 → `__` 훅 클래스나 id
  - 상태 클래스(`.on`, `.in`, `.rv`) → `is-*`
  - 시맨틱 태그, 제목 단계(h3부터), 마크업 순서(버튼·컨트롤은 콘텐츠 뒤, PC 배치는 `grid-template-areas`로), 접근성 속성
  - `dl` 안에 `dt`/`dd` 아닌 줄이 섞여 있으면 밖으로 뺀다
  - 동작 없는 버튼(전체 메뉴 등)은 동작을 붙이거나 사용자에게 묻는다
  - CSS → `#<id>` 중첩 SCSS, `px-rem`, `font-resize`, 4의 배수, 속성 순서, 미디어쿼리 중첩
  - 인라인 `style`(좌표, 크기) → 모디파이어 클래스. 좌표 목록은 SCSS 맵 + `@each`로
  - 바닐라 JS → jQuery. JS(WAAPI)로 돌리던 회전·맥동·이동 애니메이션은 가능하면 CSS `@keyframes`로 옮기고, 순서가 있는 강조만 JS로 남긴다
  - 배경 이미지 → `<img>`
- 원본의 Tailwind·Bootstrap 유틸리티는 BEM + SCSS로 옮긴다
- 원본의 PC 화면이 vw-rem 스케일과 맞는지 본다: `1281~1920` 구간은 rem이 화면에 비례해 줄어 원본 `zoom`과 같은 효과가 난다. 단 이 구간에서 rem 기준 폭이 화면보다 약간 넓어지므로(1600에서 1920rem ≈ 1690px) 고정 폭 대신 `fr`·`%`로 짜고, 한 줄 고정 큰 글자(`nowrap`)는 1600에서 한 번 줄인다

### 비교와 정리

- 가공 전/후 1920 스크린샷을 섹션 높이 2000px씩 잘라 나란히 비교한다. 전체 높이 차이가 몇 px 안쪽인지 함께 본다
- 리포트(`<id>_spec.md`)에 정리: 화면 기준(분기점별 변화), 이름 변경표, 구조 변경, 고친 접근성 문제, 원본 그대로 둔 것(확인 필요)
